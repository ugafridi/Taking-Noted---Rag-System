## Part 1. Why We Evaluate

You trained a model in Week 2. It produced predictions. The honest question that follows is: should anyone trust those predictions? Evaluation is the process of answering that question with numbers instead of feelings.

Think of a student preparing for an exam. If the teacher sets the exam using the exact same questions the student practiced, a perfect score proves only that the student memorized the answers. A fair exam uses new questions. Machine learning has the same rule.

| Word | Plain meaning |
|---|---|
| **Training data** | The examples the model studies to learn patterns, like practice questions |
| **Test data** | Examples the model never saw while learning, like the real exam |
| **Prediction** | The answer the model gives for one example |
| **Label or ground truth** | The correct answer, known by a human, used to grade the prediction |
| **Metric** | A number that summarizes how good the predictions are |

The label `Survived` is 1 if the passenger lived and 0 if not. For the rest of Parts 2 to 6, the **positive class** is 1, meaning "survived". Positive does not mean good, it only means "the thing we are looking for".

### Step 3. Train a Model and Compare Training Score With Test Score

We train a logistic regression, then score it twice, once on the data it studied and once on the data it never saw. `model.predict(...)` returns the model's answers and `accuracy_score(true, predicted)` returns the fraction that match.

If the training score is much higher than the test score, the model memorized instead of learned. This gap is the first thing to check, and it is why every honest evaluation uses test data.

The two numbers are close, so this model is not memorizing. We will use `pred_test` and `y_test` for most of the next parts. From here on, whenever we say "the model's results", we mean its predictions on the test set.

But a single accuracy number hides how the model is wrong. To see that, we need a table of its mistakes.

## Part 2. The Confusion Matrix

Almost every classification metric is built from four counts. The confusion matrix is simply the table that holds those four counts. Learn this table and the rest of today is arithmetic on it.

Take a helmet alert system on a construction site. It looks at a worker and either raises an alert ("no helmet") or stays quiet. For each worker, two facts exist: what was really true, and what the system said. Combining the two facts gives four possible outcomes.

| Outcome | Short name | Meaning in the helmet example |
|---|---|---|
| True Positive | **TP** | Worker had no helmet, system raised the alert. Correct. |
| False Negative | **FN** | Worker had no helmet, system stayed quiet. A missed violation. |
| False Positive | **FP** | Worker wore a helmet, system raised an alert. A false alarm. |
| True Negative | **TN** | Worker wore a helmet, system stayed quiet. Correct. |

A trick to read the names: the second word is what the system **said** (positive means it flagged, negative means it did not), and the first word says whether the system was **right** (True) or **wrong** (False). So "False Negative" means: the system said negative, and that was wrong.

Be careful with the word "positive". It means "the system said yes to the thing we look for", not "good news". In a cancer test, a positive result is bad news for the patient, yet the test is still called positive.

### Step 4. Build a Confusion Matrix By Hand

Before using any library, we count the four outcomes ourselves from 10 workers. In the lists below, 1 means "no helmet, should alert" and 0 means "helmet on". `actual` is the truth, `predicted` is what the system said.

The loop walks through the workers one at a time, looks at the pair (actual, predicted) and adds one to the right counter. This is exactly what scikit-learn does internally, only faster.

Read the output against the table: 3 violations were caught, 1 was missed, 2 helmets triggered false alarms, and 4 helmets were correctly left alone. The four numbers always add up to the number of examples, a quick check that you counted everything.

Now the same thing with scikit-learn. `confusion_matrix(actual, predicted)` returns a 2 by 2 array. By convention, **rows are the true class and columns are the predicted class**, ordered 0 then 1. So the layout is `[[TN, FP], [FN, TP]]`. Notice this is a different arrangement from our picture, where TP was at top left. Libraries put class 0 first, so TN sits at the top left.

`.ravel()` flattens the 2 by 2 array into one list in the order TN, FP, FN, TP, which lets us unpack the four values into names. The last line confirms the library and our loop agree. Memorize this order: **TN, FP, FN, TP**, it appears in almost every real script.

### Step 5. The Confusion Matrix of the Titanic Model

Now the real model. We pass the true test labels and the model's test predictions. `ConfusionMatrixDisplay` draws the table as a colored grid, which is easier to read than raw numbers. The darker the cell, the more passengers fall in it.

How to read it for this model, in plain sentences:

- **TN = 90**: 90 passengers did not survive, and the model correctly said so.
- **FP = 15**: 15 passengers did not survive, but the model said they would. False alarms.
- **FN = 19**: 19 passengers did survive, but the model said they would not. Missed survivors.
- **TP = 55**: 55 passengers survived, and the model correctly said so.

The matrix reveals something accuracy never will: the model makes two different kinds of mistakes, and they are not equally common (19 misses, 15 false alarms). Whether that matters depends on the problem. Every metric in the next parts is a different way of summarizing this one table.

## Part 3. Accuracy and the Accuracy Trap

**Accuracy** is the simplest summary: out of all predictions, how many were right?

$$\text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN}$$

In words: correct predictions divided by all predictions. It is easy to explain and easy to compute, which is why everyone starts with it.

### Step 6. Compute Accuracy By Hand and With the Library

We take the four counts from the Titanic matrix and apply the formula. Then `accuracy_score` computes it directly from the labels. The two should match exactly.

About 81 out of every 100 test passengers are classified correctly. That sounds decent. Now we show why you must never stop here.

### The Accuracy Trap

Suppose a bank wants to catch fraud. Out of 1000 transactions, only 10 are fraud, which is realistic: fraud is rare. Now imagine a lazy "model" that never thinks at all and always answers "not fraud". How accurate is it?

It is right on all 990 honest transactions and wrong on the 10 frauds. That is 990 out of 1000, so 99% accuracy, and it has caught zero fraud. A model that does nothing looks excellent. This is the accuracy trap: **when one class is much rarer than the other, accuracy rewards ignoring the rare class**.

### Step 7. See the Trap In Code

We build the 1000 labels, create the lazy model with `DummyClassifier(strategy="most_frequent")`, which simply always predicts the most common class, and score it. `y_fraud` has 990 zeros and 10 ones. We will look at recall for the first time here, as the fraction of real frauds the model found, explained fully in Part 4.

Accuracy 0.99, frauds caught 0.0. The matrix shows why: `[[990, 0], [10, 0]]`, all 10 frauds sit in the False Negative cell and nothing was flagged at all.

This is not only a toy. Disease screening, defect detection, intruder alerts and the shelf-empty alerts in the FreshMart case all have a rare event that matters most. Always look at the class balance first.

### Step 8. Does a Real Model Fall Into It Too?

You might think a trained model avoids this. We test that with a larger generated dataset, about 1 percent fraud, and train a real logistic regression on it. `make_classification` creates fake but realistic data with the class proportions we choose through `weights`. `stratify=` in the split keeps the same fraud proportion in both the training and test parts, which matters when one class is rare.

Accuracy is above 98 percent, yet the matrix shows only 5 of the 48 real frauds were caught (recall about 0.10) and 43 slipped through. A real, properly trained model fell into the same trap, because the easy way to be accurate on this data is to say "not fraud" almost every time.

**The lesson:** accuracy is fine only when the classes are roughly balanced and both mistakes cost about the same. Otherwise use the metrics in the next parts, which look at the two kinds of mistakes separately.

## Part 4. Precision, Recall and F1

Because the two mistakes (False Positive and False Negative) often have different costs, we measure them separately. Each metric asks a different question about the same matrix.

**Precision** looks at everything the model flagged and asks how much of it was real.

$$\text{Precision} = \frac{TP}{TP + FP}$$

Low precision means lots of false alarms. Use this when a false alarm is expensive: a spam filter that sends real emails to the junk folder annoys people, a security alert that cries wolf gets ignored.

**Recall** (also called sensitivity or true positive rate) looks at everything that was really positive and asks how much the model found.

$$\text{Recall} = \frac{TP}{TP + FN}$$

Low recall means many real cases were missed. Use this when a miss is expensive: a cancer screening that misses a tumour, a fraud system that lets fraud through, a helmet alert that misses a worker in danger.

A simple memory aid: **precision is about the quality of your alerts, recall is about the coverage of your search**.

### Step 9. Calculate Them By Hand From the Titanic Matrix

Using the numbers `tp_t`, `fp_t` and `fn_t` from Part 2, we apply each formula directly. Then we confirm with `precision_score` and `recall_score`. Do the arithmetic on paper first if you want: precision is 55 divided by 70, recall is 55 divided by 74.

Precision is about 0.79: when the model says "this passenger survives", it is right about 79 percent of the time. Recall is about 0.74: of all passengers who really survived, the model found about 74 percent of them.

Notice the denominators differ. Precision divides by everything the model **said** was positive (TP plus FP). Recall divides by everything that **really is** positive (TP plus FN). Mixing these two up is the most common mistake, so say it aloud: precision looks at the model's alerts, recall looks at reality.

### Which One Should You Care About?

| Situation | Costlier mistake | Prioritize |
|---|---|---|
| Cancer screening | Missing a real tumour (FN) | Recall |
| Email spam filter | Real mail sent to junk (FP) | Precision |
| Fraud detection | Missing real fraud (FN), but too many alerts overwhelm investigators (FP) | Recall, with a floor on precision |
| Helmet alert on a site | Missing an unprotected worker (FN) | Recall |
| Recommending a movie | A bad suggestion (FP) is mild | Precision a little more |
| Shelf-empty alert to a manager | Fifty useless alerts and the manager mutes the phone (FP) | Precision, with enough recall |

There is no universal best. You raise one by accepting a drop in the other, and the choice belongs to the people who understand the cost of each mistake. That conversation is exactly what a requirement should capture.

### F1 Score: Balancing Precision and Recall In One Number

Two numbers are awkward to compare across models. Model A has precision 0.9 and recall 0.5, model B has precision 0.7 and recall 0.7. Which is better? The **F1 score** squeezes both into one number.

$$F1 = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

This is the **harmonic mean** of precision and recall. Why not the ordinary average? Because the ordinary average hides a disaster. A model with precision 1.0 and recall 0.01 has an ordinary average of 0.505, which looks mediocre, yet the model is nearly useless because it finds almost nothing. The harmonic mean is dragged toward the smaller of the two numbers, so F1 stays low unless **both** precision and recall are decent. For that same model, F1 is only about 0.02.

### Step 10. Calculate F1 By Hand and With the Library

We reuse the precision and recall from Step 9 and apply the formula. Then `f1_score` computes it directly from the labels. The last two lines repeat the disaster example, so you can see the ordinary average and F1 side by side.

F1 is about 0.76 for the Titanic model, between its precision of 0.79 and its recall of 0.74, a little closer to the lower one, exactly as the harmonic mean should behave. In the disaster example the ordinary average says 0.505, a half decent model, while F1 says 0.02, the truth. F1 cannot be fooled by one strong number covering for one terrible one.

A metric encodes a **priority**. F1 treats precision and recall as equally important. If your problem clearly cares more about one of them, look at that one directly, as the table above showed.

### Step 11. The Classification Report: Everything In One Call

`classification_report` prints precision, recall and F1 for each class at once, plus the **support**, which is simply how many real examples of each class exist. We pass `target_names` so the rows have readable names.

Each row treats one class as the positive class. The "Survived" row is the one we computed by hand. The "Did not survive" row is the same calculation with the roles swapped, so the model looks slightly better at spotting non-survivors. The columns `macro avg` and `weighted avg` are averages of the two rows, explained in Part 5. `support` shows 105 and 74 real examples, so the classes are a bit lopsided but not extreme.

## Part 5. More Than Two Classes

Real problems often have several categories: three flower species, ten digits, five kinds of defect. The confusion matrix grows to N by N, and each class gets its own precision and recall (treat one class as positive, all the rest as negative, repeat for every class). To get one overall number, we need to average the per-class scores. There are three ways.

| Average | How it works | When it is the right choice |
|---|---|---|
| **Macro** | Average the per-class scores, every class counts equally | You care about rare classes as much as common ones |
| **Weighted** | Average the per-class scores, weighted by how many examples each class has | You want the overall score to reflect the real mix of data |
| **Micro** | Pool all the TP, FP, FN counts across classes, then compute once | For single-label problems this equals plain accuracy |

### Step 12. A Three-Class Example

We use the wine dataset bundled with scikit-learn: 178 wines in 3 classes, described by chemical measurements. A decision tree limited to depth 3 will make a few mistakes, which makes the matrix interesting. `load_wine` needs no internet.

Rows are the true class, columns are the predicted class. The diagonal (top left to bottom right) holds the correct predictions. Everything off the diagonal is a mistake, and its position tells you **which classes get confused with which**, for example "true class_1 predicted as class_2". This is far more useful than a single accuracy number, because it tells you where to improve.

### Step 13. Per-Class Scores and the Three Averages

`classification_report` shows each class. Then we ask for each average explicitly by passing `average="macro"`, `"weighted"` and `"micro"`.

Two things to notice. First, the **micro** numbers all equal the accuracy, as the table promised. Second, macro and weighted differ slightly because the classes have different sizes. To see macro is not magic, we compute it by hand: take the per-class recall values and average them with `np.mean`.

The hand average matches the library. `average=None` is a handy trick: it returns the score for every class separately so you can see which class is the weak one. Rule of thumb: report **macro** when rare classes matter, and always look at the per-class rows too.

## Part 6. Thresholds and Probabilities

So far the model gave a hard answer, yes or no. But most classifiers actually compute a **probability** first, for example "this passenger has a 0.63 chance of surviving", and then apply a rule: if the probability is above **0.5**, say yes. That cutoff is called the **threshold**, and 0.5 is only a default, not a law.

Moving the threshold changes the mistakes the model makes. Lower it and the model says "yes" more often, so it catches more real positives (recall rises) but raises more false alarms (precision falls). Raise it and the opposite happens. The threshold is the dial that lets you choose where on the precision and recall trade-off you want to be, **without retraining the model**.

### Step 14. Get the Probabilities

`predict_proba` returns two columns, the probability of class 0 and of class 1. We keep column 1, the probability of survival. Look at a few real values to see what the model is actually computing before the 0.5 rule turns it into yes or no.

Each row shows a probability, the yes or no it produces at the default threshold, and the truth. The model is confident in some cases (near 0 or 1) and unsure in others (near 0.5). A decision made from 0.51 is far less certain than one made from 0.95, and the threshold lets us treat those differently.

## Part 7. Regression Metrics

Regression predicts a **number**, so "right or wrong" no longer makes sense. A house price prediction of 305 thousand against a true 300 thousand is nearly right. We need metrics that measure **how far off** the predictions are. The core idea is the **error** (also called the residual) for one example:

$$\text{error} = \text{predicted} - \text{actual}$$

Every regression metric is a different way of summarizing the errors across all examples.

| Metric | Formula in words | Units | Key behavior |
|---|---|---|---|
| **MAE** (Mean Absolute Error) | Average of the absolute errors | Same as the target | Easy to explain, every error counts in proportion |
| **MSE** (Mean Squared Error) | Average of the squared errors | Target squared | Punishes big errors heavily, hard to interpret directly |
| **RMSE** (Root Mean Squared Error) | Square root of MSE | Same as the target | Like MSE but back in readable units |
| **R squared** | 1 minus (model error / error of just guessing the average) | No units | 1 is perfect, 0 equals guessing the average, can go negative |

## Part 8. Can You Trust the Score?

A metric is only as honest as the way it was measured. Three checks protect you from fooling yourself.

### Check 1: The Train-Test Gap (Overfitting)

A model that is very flexible can memorize its training set. A decision tree allowed to grow without limit is the classic example. We compare an unlimited tree with a shallow one. Look at both accuracy columns.

The unlimited tree scores nearly perfectly on the training data and clearly worse on the test data, a big gap, which is overfitting: it memorized quirks of the training passengers. The depth 3 tree has a smaller gap and a test score at least as good. **If you only ever looked at training accuracy, you would pick the worse model.**

### Check 2: One Split Can Be Lucky

Our test set is just 179 passengers picked by one random shuffle. A different shuffle could give a different score. How much? We repeat the whole split-train-score loop with ten different seeds and look at the spread.

The same model, the same data, and the score ranges from 0.76 to 0.855, nearly ten percentage points, just from the luck of the shuffle. So a difference of one point between two models on one split is meaningless noise. Never declare a winner from a tiny gap on one test set.

### Check 3: Cross-Validation

**Cross-validation** makes the repeated-split idea systematic. With 5-fold cross-validation, the data is cut into 5 equal parts. The model trains on 4 parts and is tested on the 5th, and this is repeated so **every part is used as the test set exactly once**. The result is 5 scores, and their average is a steadier estimate than any single split.

`cross_val_score(model, X, y, cv=5, scoring=...)` does all of it. We can ask for any metric by name, so here we score accuracy, F1 and recall.

Each row shows five fold scores, their average and the standard deviation, a measure of how much they wiggle. Report the **average and the spread**, for example "accuracy 0.79 plus or minus 0.02", instead of a single number. For classification, scikit-learn automatically keeps the class proportions similar in each fold.

### A Warning About Data Leakage

Leakage means information from the test set sneaks into training, which makes scores unrealistically good. Typical causes: scaling or filling missing values using the **whole** dataset before splitting, or having the same patient or the same image appear in both training and test sets. The safe rule is: **split first, then learn everything (averages, scalers, encoders) from the training part only**, and apply it to the test part. A leaked score is not a small error, it is a fake result.

## Part 9. Computer Vision Metrics: IoU and mAP

In object detection the model draws a **box** around each object and names it. The answer is not just right or wrong: a box can be in roughly the right place, or slightly off, or on the wrong thing. We need a way to score "how well do two boxes agree?". That measure is **IoU**, Intersection over Union.

The ground truth box is drawn by a human. The prediction is what the model produced. The overlap area is the **intersection**. The total area covered by both boxes, with the overlap counted only once, is the **union**. Dividing one by the other gives a score from 0 (no overlap) to 1 (identical boxes).

Boxes are written as four numbers `(x1, y1, x2, y2)`: the top left corner and the bottom right corner in pixels.

### Step 15. Write an IoU Function

The function finds the overlapping rectangle by taking the larger of the left and top edges and the smaller of the right and bottom edges. If the boxes do not overlap, the width or height is negative, so we clip it to 0. Then it computes the three areas. We try three predictions against one ground truth box.

Check the first one by hand: the overlap is 90 by 90 = 8100. Each box has area 10000, so the union is 10000 + 10000 minus 8100 = 11900. IoU = 8100 / 11900 = 0.6807. The model's box is shifted only 10 pixels in each direction, yet the score is already only 0.68, which shows how strict IoU is.

### From IoU To Right or Wrong

To turn IoU into a decision we pick an **IoU threshold**, usually **0.5**. A predicted box with IoU at or above 0.5 with a real object is a **True Positive**. A predicted box that matches no object well enough is a **False Positive**. A real object that no box matched is a **False Negative**. From there, precision and recall work exactly as before.

### Average Precision (AP) and mAP

Detectors also give each box a **confidence score**. Sort all the predicted boxes from most to least confident, and walk down the list. At every step you can compute precision and recall so far. This traces a curve of precision against recall, and **AP is the area under that curve**. **mAP** (mean Average Precision) is the average of AP over all classes (and sometimes over several IoU thresholds).

## Part 10. OCR Metrics: CER and WER

In Week 3 an OCR model turned an image into text. How do we score text? Accuracy as one "all or nothing" number is harsh, since getting one letter wrong in a long line makes the whole line wrong. The OCR world instead counts the **edits** needed to turn the model's text into the correct text. An edit is one of three things:

- **Substitution**: one character (or word) replaced by another,
- **Deletion**: something the model left out,
- **Insertion**: something the model added that was not there.

The minimum number of edits is called the **edit distance** (or Levenshtein distance).

$$\text{CER} = \frac{S + D + I}{\text{number of characters in the correct text}} \qquad \text{WER} = \frac{S + D + I}{\text{number of words in the correct text}}$$

**CER** is the Character Error Rate and **WER** is the Word Error Rate. Lower is better, 0 is perfect. Because insertions are counted, the rate can go **above 1** when the model writes much more than the truth.

### Step 16. Write the Edit Distance Function

The classic method fills a table. Cell `[i][j]` holds the cheapest number of edits to turn the first `i` items of the model's text into the first `j` items of the truth. Each cell is the minimum of three choices: delete, insert or substitute (a substitution costs 0 if the items already match). The function works on any list, so it handles characters (CER) and words (WER) with the same code.

A well-known check: turning "kitten" into "sitting" takes 3 edits (k to s, e to i, add g), and the function agrees. Now apply it to receipt-style OCR outputs.

### Step 17. Score Some OCR Outputs

The correct text is a line from an invoice. Four imagined OCR outputs make different mistakes: a perfect read, one letter swapped for a lookalike digit, a dropped word, and a messy read. Read both columns together: CER is gentle with a single wrong character while WER is strict, because one wrong character makes the whole word wrong.

Compare the rows. "One letter wrong" has a tiny CER (1 character in 28) but WER 0.2, since 1 word out of 5 is wrong. A confused digit like `l` for `1` is also one small character error, but in an invoice that changes the money amount, a reminder that **CER and WER treat all errors equally, while the real business cost is not equal**. The messy read has a high CER and a WER of 1.0 because every word is wrong somewhere.

### Step 18. Cross-Check With a Standard Library (Optional)

The package `jiwer` is the common tool for these scores. On Kaggle it may need `pip install jiwer`, so the cell tries to import it and politely skips if it is not available. If it runs, the numbers must match ours.

Both agree, so our function is the real thing. Practical notes when you score OCR: decide whether capital letters and punctuation count, **normalize both texts the same way** (for example lowercase and trimmed spaces), and report CER for names and codes where one character matters, WER for sentences.

## Part 11. Choosing the Right Metric

Start from **what the model outputs**, which tells you the family of metrics, then ask about the **costs of mistakes** to choose within the family.

| Problem | First check | Primary metric | Also report | Warning sign |
|---|---|---|---|---|
| Balanced classes, equal costs | Class counts | Accuracy | Confusion matrix | None big |
| Rare event (fraud, defect, disease) | Positive share | Recall and precision | F1 | High accuracy with low recall |
| Misses are dangerous (safety, screening) | Cost of a miss | Recall at a minimum precision | F1, threshold choice | Low recall hidden by accuracy |
| False alarms are costly (alerts, spam) | Cost of an alert | Precision at a minimum recall | F1 | Users muting alerts |
| Number prediction | Target range | MAE and RMSE | R squared, comparison with a simple baseline | Negative R squared |
| Object detection | IoU threshold | mAP at IoU 0.5 | Precision, recall, per class AP | Boxes slightly off but counted wrong |
| OCR and speech | Text normalization | CER or WER | Error examples | One digit wrong in an amount |

### Connecting Metrics To Your SRS

In Week 4 you wrote requirements. A requirement like "the system shall be accurate" cannot be tested. A metric makes it testable. Compare:

- Weak: "The shelf alert should be accurate."
- Strong: "On a held-out set of at least 500 shelf images from the store, the shelf-empty detector shall reach **recall of at least 0.90 and precision of at least 0.80**, measured at an IoU of 0.5."
- Strong: "The receipt reader shall have a **character error rate below 3 percent** on the 200 sample invoices supplied by the owner."

A good evaluation requirement names four things: the **metric**, the **target number**, the **data it is measured on**, and sometimes the **conditions** (threshold, IoU, language). Write all four.

### Common Mistakes Checklist

1. Reporting only accuracy on lopsided data.
2. Mixing up precision and recall (remember: precision looks at the model's alerts, recall looks at reality).
3. Judging a model on its training data.
4. Declaring a winner from a tiny difference on one split.
5. Letting test information leak into training (scaling or filling missing values before splitting).
6. Reporting a metric without a baseline to compare against.
7. Choosing the threshold by habit (0.5) instead of by the cost of mistakes.
8. Forgetting that a metric encodes a priority, so the choice must be justified.

| Threshold | The model gives a probability, you choose the cutoff |
| Regression | MAE, RMSE and R squared measure how far predictions are from the true numbers |
| Trust | Compare train and test, repeat splits, cross-validate, avoid leakage |
| IoU and mAP | Score boxes by overlap, then count right and wrong as usual |
| CER and WER | Count the edits between the read text and the true text |
| Choose with care | The metric is a priority, write it with a number into your requirement |

## Part 12. Key Terms Recap

Every term from today in plain words, grouped by topic. Use it while working on the tasks, and to check yourself before the next session.

### The Basics

| Term | Plain meaning |
|---|---|
| **Evaluation** | Checking with numbers how good a model's predictions are |
| **Training data** | Examples the model learns from |
| **Test data** | Examples held back, never seen during learning, used for the honest score |
| **Prediction** | The answer the model gives for one example |
| **Label or ground truth** | The correct answer, known by a human, used to grade predictions |
| **Metric** | One number that summarizes how good the predictions are |
| **Baseline** | A deliberately dumb model (always the most common answer, or always the average) that any real model must beat |
| **Overfitting** | The model memorized its training data, so it scores well there and badly on new data |
| **Data leakage** | Information from the test set sneaking into training, which makes scores falsely good |
| **Cross-validation** | Splitting data into k parts and rotating which part is the test set, so every part is tested once |

### Classification

| Term | Plain meaning |
|---|---|
| **Positive class** | The thing we are looking for (fraud, no helmet, survived). It does not mean good news |
| **Confusion matrix** | The table of the four outcomes TP, FP, FN, TN |
| **TP (True Positive)** | Real positive, model said positive |
| **FP (False Positive)** | Real negative, model said positive. A false alarm |
| **FN (False Negative)** | Real positive, model said negative. A miss |
| **TN (True Negative)** | Real negative, model said negative |
| **Accuracy** | Correct predictions divided by all predictions. Misleading when one class is rare |
| **Accuracy trap** | A useless model scoring high accuracy just by always predicting the common class |
| **Precision** | Of everything the model flagged, how much was real. TP / (TP + FP) |
| **Recall (sensitivity, TPR)** | Of everything real, how much the model found. TP / (TP + FN) |
| **F1 score** | The harmonic mean of precision and recall, low unless both are decent |
| **Support** | How many real examples of a class exist in the test set |
| **Macro average** | Average of per-class scores, every class counts equally |
| **Weighted average** | Average of per-class scores, weighted by class size |
| **Micro average** | Pool all counts first, then compute once. Equals accuracy for single-label problems |

### Probabilities and Thresholds

| Term | Plain meaning |
|---|---|
| **Probability output** | The model's confidence, for example a 0.63 chance of survival |
| **Threshold** | The cutoff above which the model says yes. 0.5 is only the default |

### Regression

| Term | Plain meaning |
|---|---|
| **Error or residual** | Predicted value minus actual value |
| **MAE** | Average of the absolute errors, in the target's units |
| **MSE** | Average of the squared errors. Big mistakes weigh heavily |
| **RMSE** | Square root of MSE, back in the target's units |
| **R squared** | 1 means perfect, 0 means no better than guessing the average, negative means worse than that |

### Vision and OCR

| Term | Plain meaning |
|---|---|
| **Bounding box** | A rectangle (x1, y1, x2, y2) drawn around an object |
| **IoU** | Intersection over Union. How much two boxes overlap, 0 to 1 |
| **IoU threshold** | The overlap needed to count a box as correct, commonly 0.5 |
| **AP and mAP** | Area under the curve of precision against recall for one class, and its average over all classes |
| **Edit distance** | The fewest substitutions, deletions and insertions to turn one text into another |
| **CER** | Character Error Rate. Edits divided by the number of characters in the correct text |
| **WER** | Word Error Rate. Edits divided by the number of words in the correct text |
