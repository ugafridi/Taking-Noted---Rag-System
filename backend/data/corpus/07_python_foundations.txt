## 2. Notebook Basics: Cells, Kernels, and Running Code

A notebook remembers everything you have run so far, in order, in something called the kernel.

If you define a variable in one cell, then delete that cell, the variable still exists in the kernel's memory until you restart it. If you run cells out of order, the notebook can behave unpredictably.

## 4. Lists

### Before we start: what is indexing, and why does it start at 0?

Any ordered collection in Python, including lists, tuples, and even plain text, lets you grab one item using its position, called an index. Indexes start counting at 0, not 1. This trips up almost everyone at first.

The easiest way to think about it, an index is how many steps away from the start something is, not what number it is in line. The very first item is 0 steps away from the start, so its index is 0. The second item is 1 step away, index 1.

### The technical reason, for those who want it

This is not just a style choice, it comes from how computers actually store these collections in memory. A list is stored as one continuous block of memory, and the computer finds any item using this formula, `address = start_of_block + (index * size_of_one_item)`. The first item sits right at the start of that block, zero items ahead of itself, so its offset, its index, is 0. An index is really a memory offset, not a position number.

This convention was set by the C programming language decades ago, and nearly every language built afterward, including Python, kept it, partly for consistency across languages, and partly because it makes other rules work out cleanly. For example, slicing `some_list[a:b]` always gives you exactly `b - a` items, which only holds true if counting starts at 0. Change the starting point to 1 and that neat arithmetic breaks.

Strings are ordered collections too, so the exact same indexing rules apply to text, not just lists. `word[0]` is `c`, the first character, 0 steps from the start.

### What is try and except, and why do we need it?

Sometimes you can predict that a line of code might fail, and you would rather handle that failure gracefully than let the entire program stop. `try` says attempt this code. `except` says if a specific error happens, run this instead of crashing.

Compare the two cells above carefully. Same exact mistake, same `TypeError`, but the first one stopped everything, and the second one let us print a friendly message and keep going. ### Four real scenarios

**Scenario 1: a fixed RGB color**. Why not a list? Nothing about a color's red, green, and blue values should ever change independently later in a program. A tuple's immutability is the guarantee that protects that.

**Scenario 2: a database record**. Why not a list? In a list, another part of a program could accidentally overwrite someone's ID with their name. A tuple makes that mistake impossible, the values are locked the moment the record is created.

**Scenario 3: GPS coordinates**. A location's latitude and longitude belong together permanently, a tuple prevents one from ever being updated without the other.

**Scenario 4: a fixed set of weekday names**. The five weekday names will never need to grow, shrink, or reorder, exactly the case a tuple is built for.

Use a list when a collection needs to grow or shrink. Use a tuple when the values belong together permanently, as one fixed unit.

## 6. Sets

### What is a set?

An unordered collection of unique values, duplicates are removed automatically.

Notice the output only shows `{1, 2, 3}`. As Python builds this set, it checks every new value against what it already has. The second `2` and the second and third `3` are equal to values already present, so they are silently dropped, not counted, not flagged, just skipped entirely.

### What happens if we add a value that already exists?

Nothing changed, and no error appeared. This is different from every error we have seen so far. Adding a duplicate to a set is not a mistake as far as Python is concerned, it is simply ignored. A set never complains about duplicates, it just quietly keeps one copy, forever.

### Checking membership

### The most common set error

`TypeError`, set object is not subscriptable. A set has no order, so position 0 has no meaning, unlike a list or tuple. If you need order, use a list. If you only need uniqueness and fast checking, a set is correct as is.

### Four real scenarios

**Scenario 1: deduplicating user IDs**. Without a set, you would need to write your own loop checking each ID against every ID already collected. A set does this automatically, because it refuses duplicates by definition.

**Scenario 2: allowed file extensions**. Why not a list? A list checks membership by looking at every item one at a time until it finds a match. A set checks almost instantly no matter how large it grows, which matters once you are checking against thousands of allowed values.

**Scenario 3: comparing two customer groups**. Without set operations, comparing two customer lists would mean writing a loop and a conditional together by hand. `&` and `|` do the same job in one line.

**Scenario 4: tags on a blog post**. A post's tags should never list the same tag twice, a set enforces that automatically, with no extra code needed.
